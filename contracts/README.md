# contracts/ — VaultProbe

Research-probe для гейта R1-R5 + R6mech (проверка спеки HyperEVM Epoch Vault, подпроект #0) и, с v2, для пробы
выплаты пула (R8/R10/S1/S2/UCT, план `docs/superpowers/plans/2026-10-17-pool-probe-deploy-verify.md`, шаги 1.1/1.2/1.6).
НЕ вольт: нет долей, нет комиссий, один owner. На mainnet деплоится ТОЛЬКО драйвером `analysis/e104_mainnet_pool_probe.pytxt`
руками оператора (потолок суммы, одноразовый кошелёк, ключ только из env); иначе — testnet.

**v2 (17.10) только добавляет функции**, прежние сигнатуры целы (их зовёт e96):

| Функция | Что | Прекомпайл / действие |
|---|---|---|
| `spotSend(to, token, weiAmount)` onlyOwner | spot-перевод с Core-счёта контракта на чужой Core-адрес (путь выплаты `claim`); перевод себе — отказ библиотеки | CoreWriter action 6 |
| `spotBalanceOf(user, token)` | `total`/`hold`/`entryNtl` ЛЮБОГО адреса в Core-wei | `0x…0801` |
| `marginOf(user)` | `accountValue`/`marginUsed`/`ntlPos`/`rawUsd` ЛЮБОГО адреса, dex 0 (как `PoolVault.reconcile` читает ноги) | `0x…080F` |
| `positionOf(user, perp)` | позиция ЛЮБОГО адреса по perp-индексу | position2 `0x…0813` |

Тесты v2 — `VaultProbeTestSim` (симулятор HyperCore, офлайн): доходит ровно на сумму, не-owner — `NotOwner`, перевод себе
отклоняется, чужой баланс/маржа/позиция равны заданным.

`src/BlockWitness.sol` (e103 T1(а), 18.10) — свидетель видимости по блокам: `record(a, b, token, tag, keepGas)` читает
spot двух адресов, маржу и `withdrawable` первого и пишет событие `Seen` с `block.number`, затем сжигает газ до `keepGas`
(две `record` не помещаются в один малый блок -> очередь ложится по одной на блок). Денег не держит. Тесты —
`BlockWitnessTest` (прекомпайлы замоканы). ⚠ `record` в тесте зовётся с явным газом: `gas_limit` профиля 2^63, без лимита
цикл сжигания не кончается.

`src/VaultProbe.sol` оборачивает `hyper-evm-lib` (CoreWriterLib/PrecompileLib) фиксированными
внешними сигнатурами: их зовёт по имени `analysis/e96_vault_research_gate.pytxt` через `cast`
(EVM-сторона гейта), поэтому сигнатуры менять нельзя без синхронной правки драйвера.

Foundry ставится не через `forge`/`foundryup` в PATH, а по адресу из `HL_FOUNDRY_BIN`


## Кто вызывает

`analysis/e96_vault_research_gate.pytxt` (`deploy`/`r1`..`r5` команды) — деплоит `VaultProbe`
и шлёт транзакции через `cast send`/`cast call` теми же внешними сигнатурами, что и в тестах.

в argv, ни в окружение дочерних процессов (у `cast send --private-key` в Foundry 1.8.1 env-источника нет).

# PoolLedger — бухгалтерия пула (контракт #2, этап 1)

`src/PoolLedger.sol` — перенос 1:1 эталона `runtime/vault_accounting.pytxt` (класс `GenLedger`, **редакция 9.4 «замороженный пул» + 9.3.1.1 + пакет безопасности**; раздел «Ред. 9.4» ниже). Денег и
HyperCore в нём нет: суммы — числа, как в эталоне. План работ: `docs/superpowers/plans/2026-10-08-pool-contract-2.md`,
правила ред. 9 — спека `docs/superpowers/specs/2026-09-20-pool-vault-rev7-design.md`, глава 8.

Ред. 9 / 9.1 в контракте: недельный расчёт в ДВЕ фазы (строки адресов -> реферальные доли после всех строк -> возвраты
доплатившим с цепочкой -> раздел недостачи -> закрытие поколений -> очередь; фаза 2 — этапами пачками, см. ниже); недостача сверх денег адреса доплачивается
соучастниками того же поколения одним кругом по весу снимка, остаток — «весь пул» по min(капитал, S), остальное — дыра
(`shortfall`); книга доплативших `cred`/`credPool` (во внешнем виде — нулевой адрес = счёт пула); долг гасит только
прибыль самого должника; `hold` (верхняя граница доплаты) вычитают вес, резерв и свободное; гейт депозита — признанный долг
плюс вся проектная недостача по маркам; treasury инвестором не бывает; автовывод уносит весь котёл. **Удалено** (ред. 8):
операторы и их замок (`initOperator`), `operatorCover`, `fundTreasury`, `repayDebt`, подушка котла (`_treasuryNeeded`,
`_treasuryFree`), покрытие убытка котлом. `_debtFree` заменён на `_noProjectedLoss` (доказывает «проектного убытка нет ни у
кого» за O(поколений); иначе честный обход). Ред. 9.2 — зачёт циклов книги доплативших и слияние работ очереди возвратов
(раздел «Ред. 9.2» ниже). Ред. 9.2.1/9.2.2 — вес и контекст `hold` видят фазу 2 того же расчёта (возврат доплатившим),
гейт по маркам при долге; пакет безопасности — минимум депозита, предел адресов, сжигание ref; ред. 9.3/9.3.1/9.3.1.1 —
частичное закрытие `reducePosition` и комиссия с итога сделки (разделы ниже).

Судья — дифференциал `diff/pool_ledger_diff.pytxt`: поднимает `anvil` (с настоящим лимитом EIP-170), проигрывает все 70
фикстур v9 `tests/fixtures/vault_accounting/` (с фикстурами аварии ред. 9.4 — 236–239, 260, 261; исключений нет) вызов за
вызовом и сравнивает принятие вызова, всё состояние (с книгой доплативших, после заморозки — с ключом `emergency`),
результат вызова с `result` (`emergency_due`) и витрины (допуск 0). Сценарии ред. 9.1 (цепочка возврата, недостача недели у получателя возврата, порядок
зачисления, доля крошечного соучастника, «весь пул» только капиталом, порядок должников, реферальная доля после строк) —
скриптовые фикстуры эталона 213–220; зачёт циклов ред. 9.2 — 221–224 и сценарии `cycle_*` (`--cycles N`, ниже). Фикстуры держат в очереди не больше 5 заявок, поэтому очередь судят ещё и сценарии
`queue_NNN` (`--fuzz N`): их вызовы и трассу генерирует ЭТАЛОН (суммы — по его состоянию; много мелких выводов по кругу,

Фикстуры идут параллельно (`--jobs`, каждая — своя цепь). Заявки очереди нормальная форма сортирует по id (у контракта они
лежат по ключам, порядок FIFO — по id), выгрузка с двумя одинаковыми id или с заявкой <= 0 — отказ.

Мутант обязан покраснеть на фикстуре или сценарии очереди — атомарным расчётом или пачками; если все зелёные — судят
forge-стенды `PoolLedgerTest` (числа в них посчитаны эталоном). Эквивалентные мутанты сняты с объяснением в самом списке.
Сжатия очереди больше нет, и его аналог — «мёртвые записи за снятым хвостом не отбрасываются перед новой заявкой» и
«выплата не сдвигает голову ключа» — меняет числа (ловят сценарии очереди). Мутанты, меняющие ТОЛЬКО газ («подсказка новой
головы не используется», «догадка поиска упора — середина»), дифференциал не видит по построению: он судит числа, а ответ
поиска от подсказки и догадки не зависит; их цену видит только бенч газа — в список они не внесены.

Раскладка: `PoolLedgerBase` — состояние и вся внутренняя математика; `PoolLedger` (21 715 Б) — изменяющие операции и
проход очереди; `PoolLedgerMonday` (24 206 Б) — недельный расчёт (обе фазы) и книга ордеров (`fillOrder`, `cancelOrder`,
`markPosition`, `closePosition`, `reducePosition` — их писатели ведущихся сумм в PoolLedger не помещаются); `PoolLedgerViews`
(14 513 Б) — витрины, `params()`, `limits()`, `status()`, `mondayProgress()`, `dump()`; `PoolLedgerProj` (14 421 Б) — ПРОЕКЦИИ «как если
бы расчёт прошёл сейчас по маркам»: контекст `hold` гейтов (`holdCtx()`) и веса снимка (`weights()`), оба — с черновиком
фазы 2 `_repayProjection`. Все три реализации исполняются делегированным вызовом на памяти `PoolLedger`: витрины и
проекции — через fallback (селекторы `holdCtx()`, `weights()` — проекциям, остальное — витринам), расчёт и книга ордеров —
через одноимённые заглушки. Конструктор принимает параметры структурой `PoolLedger.Init` (13 статических полей кодируются в
ABI ровно как плоский список; плоские 13 аргументов не помещались в стек декодера). Хвост расчёта —
проход очереди (эталон: `_finalize_generations`, затем `_pay_fifo`) — `monday()`/`mondayEnd()` исполняют в самом PoolLedger
сразу после реализации: код очереди живёт в одном контракте. Адреса реализаций и ВЛАДЕЛЕЦ передаются конструктору
(`PoolLedger(…, viewsImpl, mondayImpl, projImpl, owner)`, память, сеттеров нет): бухгалтерия деплоится отдельно, до
хранилища, и её владелец — вычисленный адрес хранилища (раздел «Схема деплоя»). В ABI витрин и проекций допустимы только
view/pure — проверяет сверка (C6, при каждой сборке дифференциала); раскладка памяти всех реализаций одна — сверка (C9).
Лимит EIP-170 — 24 576 Б; превышают его только контракты симулятора HyperCore из `lib/` (`CoreExecution`, `HyperCore`), они
в цепь не деплоятся.

**Проекции — в отдельной реализации (18.10, место под ред. 9.2.1/9.2.2).** В 9.2.1/9.2.2 вес `sizeOrder` и контекст
`hold` гейтов (вывод, забор, выплата очереди, витрины) видят проекцию фазы 2 — черновик `_pay_back` на копии книги.
Контекст `hold` строит `_holdCtx`, и до 18.10 он был вшит в каждую реализацию, которой нужен (`PoolLedger` и
`PoolLedgerViews`): рост проекции лёг бы в обе, а у `PoolLedger` запас был 2 377 Б. Теперь его считает ОДНА реализация
`PoolLedgerProj` (`_holdCtxLocal`), а `_holdCtx` остальных — статический вызов бухгалтерии самой себя: fallback отдаёт
`holdCtx()` проекциям делегированным вызовом на той же памяти, ответ — ABI-кодированный контекст. Граница «проектного
убытка нет» (`_noProjectedLoss`, O(поколений)) судится ДО вызова — тогда контекст пуст и вызова нет. Числа те же
(дифференциал 1:1 на всех фикстурах обеих форм расчёта); газ — ниже. Ред. 9.2.1 перенесена туда же — раздел «Ред.
9.2.1 / 9.2.2» ниже. Мутанты маршрута: «fallback отдаёт `holdCtx()` витринам», «fallback отдаёт `weights()` витринам»,
«быстрый путь берётся всегда» (`mutants --all`).

Газ раскладки (`diff/pool_ledger_gas.pytxt run --n 50 [--debt]`, до → после, максимум вызова): операции без проектного
убытка — без изменений (быстрый путь); с проектным убытком (контекст обходит всех) — `withdraw` 2 254 194 → 2 314 482
(+2.7 %), `payQueue` 2 081 869 → 2 142 170 (+2.9 %), `claim` 2 037 909 → 2 098 264 (+3.0 %): цена ABI-кодирования
контекста (~1.2 тыс. газа на участника); `sizeOrder`, `monday`, `markPosition`, `closePosition`, `deposit` — без изменений.

Нулевой адрес участником не бывает (эталон `_addr`): `deposit`, `withdraw`, `claim`, `setPayoutMode`, `setPartner`,
`initPartner`, конструктор (`treasury`) и витрины адреса отклоняют его с `Revert("zero address")`. В `deposit` нулевой
реферал — это «реферала нет» (None эталона).

## Что стоит O(входа) и как это ограничено

Неделимая единица любой транзакции не должна обходить то, что растёт без границы. Что для этого хранится иначе, чем в
эталоне (числа — те же, судит дифференциал):

- **Очередь заявок** — не общий массив, а полоса сумм на ключ (адрес, reward): запись i покрывает (end[i-1], end[i]], живая
  часть ключа — (P, P + queued]. Выплата снимает с головы (P растёт), каскад убытка — с хвоста (queued падает): это ровно
  порядок эталона (FIFO по id и «новейшие первыми»), а снятие стоит O(1) при любом числе заявок (находка M1: каждый
  доплативший раньше обходил и сжимал весь массив). Мёртвые записи за снятым хвостом отбрасывает следующая заявка ключа.
- **Проход очереди** (`_payFifoWith`) — по адресам, а не по заявкам: выплата адресу снижает только его `_room` и ровно на
  выплаченное, ликвидность — тоже, а `_fundClaimable` от нарезки не зависит. Хватает ликвидности на всех — каждому
  min(заявки, `_room`); не хватает — двоичный поиск по id заявки, на которой поток упирается в бюджет (`_fifoPay`; первые две
  пробы — по обе стороны линейной оценки, внутри ключа — догадка по доле диапазона). Стоимость — O(ключей × log), от числа
  заявок почти не зависит.
- **`col` эталона не хранится**: вне фазы строк он равен доле `rMon` поколения; хранится сумма по адресам `colSum`. Начало
  фазы 2 и закрытие поколения — O(поколений); веса закрытого поколения не стираются (номер не повторяется, после
  `snapExists = false` их не читает никто). Живые ордера поколения — счётчик `genLive`. Снимок — без списка адресов:
  участники — `order[0..snapN)` с ненулевым весом (находка M2: `mondayEnd` и `_phase2Begin` обходили G × N).
- **Ведущиеся суммы адреса** (`aggPend`, `aggU`, `aggPL`, `aggEx`): неразнесённое, доля upnl, бумажный убыток и удержание.
  Их пишут только `_aggOrder` (вклад ордера снимается до изменения и прибавляется после, O(снимка) на sized/mark/close/
  cancel) и `_aggR`; строка расчёта сверяет сумму с обходом поколений (`_settle: pending sum` — fail-loud). Проекция адреса —
  O(1) вместо O(ордеров): при N=200 и 60 поколениях с марками `withdraw`/`claim`/`deposit` стоили 94–101 млн, теперь 8 млн.
- **Буферы фазы 2** (`monRepay*`, `monRef*`, `monDebt*`, `monDebtLoss`, `monCov`) — со своей длиной; позиция должника и доля
  «всего пула» — с меткой недели. `_mondayBegin` обнуляет длины, `mondayEnd` ничего не стирает (находка M3, часть про
  очистку: удаление `monRepayA/X` при 4998 работах стоило 40.6 млн).
- **`hold`**: сумма слагаемых, дошедшая до границы min(U + пыль, вместимость), дальше не считается; вес адреса в поколении
  читается один раз; позиция поколения — двоичный поиск.

## Недельный расчёт пачками (keeper)

`mondayBegin` -> `mondayStep(k)`, пока этап не станет 7 -> `mondayEnd`. Пока расчёт открыт, любая другая операция
отклоняется (`monday in progress`), `mondayEnd` до конца этапов — `monday: not all settled`, `mondayStep(0)` —
`mondayStep: k == 0` (раньше на этапах 0/1/2/3/5 он молча отвечал «осталось > 0», а на этапе 4 всё равно двигал расчёт).
`monday()` — те же этапы одним вызовом (без ограничения пачки; годится для малых пулов). `mondayStep` ведёт этапы по
очереди: одна пачка — до `k` единиц ТЕКУЩЕГО этапа, через границу этапа не переходит, пустые этапы проходит сразу; ответ —
сколько единиц осталось у этапа, на котором расчёт стоит после пачки. `mondayProgress()` (витрина) — `(этап, сделано,
осталось, открыт)`; по этапу keeper выбирает `k`:

| Этап | Что | Единица пачки | `k` при N=200 (максимум за транзакцию, замер) |
|---|---|---|---|
| 0 | ФАЗА 1: строки адресов (результат, гашение своего долга, комиссия, каскад убытка) | участник | 100 при малом G (~11 млн); 20 при G=60 (~7.2 млн) |
| 1 | реферальные доли недели — после всех строк | доля | как у этапа 0 |
| 2 | возвраты доплатившим с цепочкой (очередь растёт по ходу) | работа очереди | 1 (~4.9 млн) |
| 3 | раздел недостачи между соучастниками | (должник, поколение его убытка) | 1 (до 16.4 млн) |
| 4 | «весь пул»: потребность S, доли плательщиков, покрытое у должников | один вызов | — (до 9.3 млн) |
| 5 | строки таблицы «весь пул» и дыра | должник | 1 (до 9.7 млн) |
| 6 | ред. 9.2: доли раздела — в книгу (должник по регистрации, доплативший по адресу), за каждой записью зачёт цикла | запись доли или один поиск пути | 1 (до 4.1 млн — цикл через весь пул; 2.2 млн — 199 долей одного должника) |

Исход не зависит от нарезки на пачки: каждая пачка продолжает с того места, где остановилась предыдущая. Входы, которые

убытка), невместившееся начатого должника переживает конец пачки (`monMatesR`), строка книги сбрасывается в конце должника

## Ред. 9.2: зачёт циклов книги доплативших

Эталон (спека 8.10, `_cover` -> `_net_cycles`, `_pay_back`): книга доплативших между инвесторами всегда ациклична. За каждой
записью долга a -> b — зачёт: пока a должен b, у b есть свои долги перед инвесторами и есть путь долга b -> … -> a (кратчайший,
обход в ширину, соседи в порядке регистрации), каждое ребро цикла уменьшается на минимум по циклу, `uncovered` каждого
участника — на ту же сумму; деньги и `cumPnl` не двигаются. Счёт пула — не вершина. В очереди возвратов работа получателя,
который уже стоит и не исполнен, получает прибавку, а не вторую работу. Перенос:

- **Порядок записи — как в эталоне.** Эталон пишет доли раздела в книгу по одной, отсортировав пары (должник по
  регистрации, доплативший по адресу; адрес в нижнем регистре сортируется как число), и поиск пути видит книгу ровно на момент
  своей записи. Поэтому этапы соучастников (3) и таблицы (5) больше не пишут `cred`, а копят доли в `monPend`/`monPendBits`;
  новый этап **6 (`MS_NET`)** переносит их в книгу в этом порядке и за каждой записью зачитывает цикл. Деньги этапы 3 и 5
  снимают, как прежде (зачёт денег не двигает, а раздел книгу не читает). `MS_DONE` теперь 7.
- **Рёбра — битовая строка должника** (`credBits`: бит i — `cred[x][order[i]] > 0`), единственный писатель — `_credAdd`.
  Поиск пути (`_debtPath`/`_expand`) держит посещённые битовой строкой в памяти: раскрытие вершины — одно чтение слова её
  рёбер (при n <= 256), новые соседи — `биты & ~посещённые`, по порядку регистрации — от младшего бита. Весь поиск —
  O(посещённых × ⌈n/256⌉) чтений хранилища, а не O(n²). Проверка «у доплатившего нет своих долгов перед инвесторами» — одно
  слово (`_hasInvDebt`), и если долгов нет, поиска нет. Та же строка сократила работу возврата (`_repayItem`): она читает
  только существующие рёбра должника.
- **Единица этапа 6** — запись доли или один поиск пути (с вычетом найденного цикла); проверка-отказ единицей не считается.
  Зачёт без состояния: пачка ищет путь по текущей книге, поэтому исход от нарезки не зависит (`monNetB` — доплативший,
  чей зачёт начат прежней пачкой). Поиск даже через весь пул (N = 200, путь длины 199, 200 рёбер) — 4.1 млн, пачками
  поиск делить не понадобилось.
- **Слияние работ возврата** — `monRepayPos[адрес] = week << 128 | (позиция + 1)` (по образцу `monDebtPos`): получатель,
  чья работа стоит дальше исполняемой, получает прибавку к ней. Со слиянием и ацикличной книгой работ очереди не больше n².
- **Сценарий ревьюера** (цикл A <-> B на долларовой шкале, фикстура 221): до ред. 9.2 этап возвратов третьего расчёта —

## Ред. 9.2.1 / 9.2.2: вес и гейты видят фазу 2 того же расчёта

Эталон (спека 8.11–8.11.3): вес адреса — капитал после расчёта недели по текущим маркам, а во второй фазе этого же расчёта
доплатившему приходит возврат (8.3). Перенос 1:1:

- **Вес** (`_weightOf`, `_weightsLocal`): `min(капитал, max(0, капитал + результат по маркам − гашение своего долга −
  комиссия) + возврат в капитал)`; гашение своего долга — `min(max(0, pend − бумажный убыток), долг)`, а не из одного
  закрытого (`_projected`, ред. 9.2.1). Граница доплаты веса — раздел ПОСЛЕ возвратов: вместимость и база включают возврат в
  капитал и заявки (`ph.money`), недостача — за вычетом той, что погасит пришедший возврат (`ph.cut`), проекция адресов —
  расчёт РАЗОМ (`_projected(now_ = true)`, 9.2.2). Веса одного состояния — один вызов `weights()` (PoolLedgerProj):
  `sizeOrder`, витрины `weight` и `sizingCapital` берут их статическим вызовом бухгалтерии самой себя.
- **Гейты** (`holdCtx()`: вывод, забор, выплата очереди, витрины): вместимость и база тоже с возвратом (`ph.money`),
  недостачи прежние; **гейт по маркам при долге** (9.2.2) — бумажный убыток должника гасится только `max(0, закрытое −
  гашение долга)` (`_projected(now_ = false)`): это `uncovered`, `pending_loss`, `projectedShortfall` и гейт депозита.
- **Черновик фазы 2** (`_repayProjection`, эталон `_repay_projection` на копии книги) — в памяти, без копии состояния:
  узлы (адреса) заводятся ЛЕНИВО — у должников в плюсе и у получателей возврата; строка книги должника читается из памяти
  контракта один раз, при его первой работе; очередь работ — кольцо на n мест (ждущая работа адреса одна — слияние эталона);
  деление — то же правило `_split` в чужих буферах (`_splitInto`, память не растёт с числом работ). Пусто (`any = false`) —
  ни у одного должника нет положительного результата: тогда вес — прежняя формула, а `_noProjectedLoss` по-прежнему снимает
  контекст гейтов (раздела без недостач нет — возврат его не меняет). **Быстрый путь веса без контекста больше не берётся
  мимо возврата**: вес всегда считает PoolLedgerProj.
- **Точный результат недели по маркам** (`_settleDelta`: вес адреса в каждом поколении с бумажным убытком) читается, только
  когда ответ от него зависит. Границы: `pend − aggPL <= результат <= pend` — доля = floor(s·x/T) при любом знаке x,
  floor(a + b) >= floor(a) + floor(b), поэтому доля суммы бумажных убытков поколения не меньше суммы долей по ордерам
  (`aggPL`). Значит, `pend <= 0` — возврата нет; `pend − aggPL >= долга` — гасится весь долг; `pend − aggPL + свои деньги
  >= 0` — недостачи нет. Иначе — точно. На книге «обратный треугольник» при G = 60 это снимает ~12 тыс. чтений `snapW`.
- Горячий путь черновика (`_splitInto`, `_rpTo`, `_rpPay`) — на ассемблере без проверок границ массивов: индексы дал сам
  `_splitInto` (`k < длины строки`), получатель — бит строки книги (`b < n`, проверяется), суммы в uint128. Деление при
  суммах вне uint128 — тот же раздел через `_mulDiv` (`_splitWide`; в бухгалтерии таких сумм нет — капиталы держит потолок
  uint128). Замер на треугольнике n = 40 (G = 1): один вызов `weights()` — 23.9 млн на Solidity, 12.0 млн с ассемблером в
  этих трёх функциях и с границами результата.

## Пакет безопасности в бухгалтерии (П1–П3, план `2026-10-17-pool-safety-pack`)

- **Параметры** `minDeposit` и `maxInvestors` — в памяти (не immutable: реализации исполняются делегированным вызовом на

## Ред. 9.4: замороженный пул (аварийный выход, правило E с КЕ13′)

Эталон — спека 8.13 и стыки 8.14 (`emergency_freeze`, `emergency_split`, `emergency_treasury`, `emergency_foreign`,
`emergency_m_cum`, `serve_starved`); план доверия §4.3–4.7 (триггеры, КЕ10, В4, В7′, В8, В12); решения КЕ15 (правило E с
КЕ13′; E′ и E_g не перенесены). Кода две части — бухгалтерии и хранилища.

**Бухгалтерия (`PoolLedgerEmergency`, пятая реализация на памяти `PoolLedger`).** `emergencyFreeze()` необратима: флаг
`emState` в `_start()` отклоняет каждую изменяющую операцию (`frozen`), шаги расчёта (`mondayStep`, `mondayEnd`) судят его в
заглушках `PoolLedger`, `initPartner` закрыт `initialized`; повторная заморозка — отказ. Итоги снимка (F_T, H, E, S, P) —
`emergencySnapStep(k)` пачками по держателям (`_holderAt`: инвесторы, затем `known`); P = Σ `snapTotal` живых поколений
(O(G) на заморозке). Доли адреса не копируются: вне открытого расчёта замороженная бухгалтерия неизменна, `f`, `s` читаются из
неё за O(1) (`_emLive`: s = stake + заявки, f = «к получению» + вознаграждение во всех плоскостях; резерва комиссии и `partR`
в наборе нет — MX2), `p` — Σ весов по живым поколениям (читается только в ветке S = 0). Правило E — витрина `emergencyDue(a, M)`
в `PoolLedgerViews`: `due_T = max(0, min(F_T − H, M − F_o))`, `r = M − due_T`, убыток `floor(r·(f+s)/E)`, прибыль
`f + s + floor((r−E)·s/S)`, S = 0 — по `p/P`, нет и их — котлу; адрес вне снимка — 0; `_mulDiv` 512 бит, вниз; минимумов нет
(MX3). Витрины: `emergencyPlanes(a)`, `emergencyTotals()`, `emergencyDump()` (ключ `emergency` эталона — ОТДЕЛЬНО от `dump()`:
хвост той читают стенды и keeper), `oldestQueued()` (В7′).

**Где снимок «до monday» (заморозка посреди расчёта).** Эталон считает расчёт атомарным; строки и фаза 2 переписывают
капитал, котёл, вознаграждения и долг пула. Решение: **MS_SNAP одной транзакцией в `mondayBegin`** — заглушка зовёт
`PoolLedgerMonday` (открытие), затем `PoolLedgerEmergency.mondayBegin` (копия `f`, `s` каждого держателя в `msFv`/`msSv` и
итогов; пишется и ноль). Заморозка при `mondayOpen` берёт копию (`emCopy`), снимок готов сразу. Веса `p` расчёт до
`mondayEnd` не трогает (`_finalizeGenerations` — в нём). Почему так: (1) у `PoolLedgerMonday` 370 Б (теперь 303) — копия туда
не помещается; `PoolLedgerViews`/`PoolLedgerProj` судятся «только view»; запас `PoolLedger` отведён пакету и `mondayAbort` —
отсюда отдельная реализация; (2) этап MS_SNAP ПАЧКАМИ (первая редакция) менял ход шагов (`mondayProgress`, число пачек) —
покраснели 13 стендов расчёта, тот же сдвиг получил бы keeper; копия при первой записи потребовала бы врезки во все пути
записи `PoolLedgerMonday`; (3) держателей при границе адресов 50 — не больше ~101: копия в `mondayBegin` стоит 3.44 млн газа
(стенд ниже). ⚠ Поднимать `MAX_INVESTORS_BOUND` — вместе с пачками копии. Атомарный `monday()` копию не пишет: открытого

**Хранилище (`PoolVaultEmergency`, делегированный модуль КЕ10).** Исполняется `delegatecall` из fallback `PoolVault`; его

## Газ ред. 9.2.1 и граница `MAX_INVESTORS_BOUND` (было 50; с ревью 20.10 — 43, раздел «Ревью 20.10», пакет A)

Проекция фазы 2 исполняется в КАЖДОЙ транзакции, которой нужен вес (`sizeOrder`) или контекст `hold` гейтов (`withdraw`,
`claim`, проход очереди при проектном убытке), и её цена — работа `_pay_back` на книге, то есть до O(n³) кандидатов `_split`
и E <= n²/2 холодных чтений рёбер книги. Пачками её не разрезать без второго, хранимого черновика (запись каждого ребра —
20 тыс. газа), поэтому транзакция ограничена числом адресов. Худший проверенный вход — **«обратный треугольник»** (стенд
`test_rev921_triangle_*`, PoolLedgerGasTest; та же конструкция — сценарий дифференциала `triangle_012`): неделя k — новый
A_k выходит до убытка, его недостачу доплачивают все прежние, затем все пополняют капитал; неделя замера — прибыль по 1 USD

## Что всё ещё растёт со входом

Ни одно из этого не растёт с числом заявок, поколений или звеньев цепочки неограниченно внутри ОДНОЙ единицы при N <= 200
в замеренных сценариях, но границы есть, и они названы:

- **Проход очереди при упоре посреди потока** (`payQueue`, `withdraw`, `treasuryPayout`, хвост `mondayEnd`) —
  O(ключей с заявками × (`_room` + log заявок)): 23.5 млн при 199 ключах — от m не зависит, но запаса мало; по разложению
  (≈0.12 млн на ключ) 25 млн — около 210 ключей с заявками.
- **`sizeOrder`** — новый снимок пишет вес каждого участника: 17.4 млн при N=200 (~87 тыс. на участника, 25 млн — около 290).
  При должниках по маркам вес каждого участника вычитает `hold`: + O(N × поколений убытка первого должника) чтений, а в
  худшем случае (недостачи по 1 микро, граница не достигается) — O(N × должников × их поколений убытка) в памяти: замер до
  ранней остановки — 43 / 66 / 147 млн при 20 должниках и G = 10 / 20 / 60; с ней на сценарии бенча — 18.8 / 23.3 / 15.9.
  То же правило `hold` у прохода очереди, когда должники по маркам есть, а ключей много.
- **Контекст `hold`** (`withdraw`, `claim`, `deposit`, `sizeOrder`, проход очереди при проектном убытке) — O(N + должников
  по маркам × (поколений + открытых ордеров)): 14.4 млн при 20 должниках и G=60, ~0.34 млн на должника — около 50 должников
  по маркам при G=60 выйдут за 25 млн (оценка по разложению, не замер).
- **Пачка соучастников** — снятие доплат со всех плательщиков в конце пачки: ~82 тыс. на доплатившего, 16.4 млн при 199
  (25 млн — около 300 доплативших у одной пачки).
- **Таблица «весь пул»** — пачка пересчитывает остатки столбцов из всех строк: O(должников × плательщиков), 9.7 млн при 20
  должниках.
- **Строки фазы 1** — O(поколений + ордеров) на участника, пачку выбирает keeper (G=60 — `k` = 20).
- Растут без границы, но читаются только витриной `dump()` (eth_call): `closedPidList`, `ledgerRefList`, `known`. С ревью-2
  (#3) keeper читает историю постранично (`closedPids`, `ledgerRefs`, `isClosedPid`, `isLedgerRef`), а состояние — `dumpState()`
  без истории.
- **Этап зачёта (6)** — единица: запись доли или один поиск пути. Поиск — O(посещённых × ⌈n/256⌉) чтений, вычет цикла —
  O(длины цикла) записей: при N=200 через весь пул 4.1 млн (~20 тыс. на ребро цикла; 25 млн — цикл около 1200 рёбер, то
  есть n около 1200). Каждая пачка заново собирает и сортирует ждущие доли текущего должника: O(m log m) при m долях
  (2.2 млн при 199). Число единиц на одну запись — до числа рёбер, которые зачёт обнуляет (каждый шаг обнуляет хотя бы
  одно), — пачками, не в одной транзакции. При n > 256 слов на вершину больше одного: поиск — n/256 чтений на раскрытие.
- **Слияние работ возврата** ограничивает этап 2 n² работами на расчёт (книга ациклична); каждая — `_split` по n + 1
  весам в памяти, чтения хранилища — только по рёбрам должника.

## Схема деплоя (КЕ10 / A4): части отдельно, хранилище последним

До 18.10 конструктор `PoolVault` сам создавал `PoolLedger` и обе ноги, и initcode хранилища (47 339 Б) нёс их код
создания — 2 КБ до лимита EIP-3860 (49 152). Теперь каждая часть — своя транзакция создания, а хранилище получает их
адреса конструктором (`VaultInit.ledger`, `legA`, `legB`) и хранит `immutable`.

**Порядок — с ОДНОГО ключа деплойера, подряд, без других транзакций между шагами 4 и 7:**

| шаг | что | аргументы конструктора |
|---|---|---|
| 1 | `PoolLedgerViews` | — |
| 2 | `PoolLedgerMonday` | — |
| 3 | `PoolLedgerProj` | — |
| 4 | `PoolLedgerEmergency` (ред. 9.4) | — |
| 4b | `PoolLedgerBook` (ред. 9.5: книга ордеров) | — |
| 5 | `PoolLedger` | treasury, bps, `partnerTermWeeks`, адреса шагов 1–4b, **owner = V**, `maxGens` (ред. 9.5, `1..MAX_GENS_BOUND`) |
| 6 | `TradingLeg` (нога A) | **vault = V** |
| 7 | `TradingLeg` (нога B) | **vault = V** |
| 8 | `PoolVaultEmergency` (ред. 9.4) | сроки `T_stuck`, `T_dead`, `T_nomonday`, `T_serve`, `T_queue_max` (каждый >= `2·DELAY`, ревью-2) |
| 9 | `PoolVault` | `VaultInit{ledger, legA, legB, admin, keeper, guardian, delay, tvlCap, legShareBps, emergency}` |

`V = CREATE(деплойер, nonce шага 9)` вычисляется ПЕРЕД шагом 5 (`cast compute-address --nonce <n+4> <деплойер>`, где `n` —
nonce деплойера перед шагом 5). Реализации (шаги 1–4b) от `V` не зависят, модуль аварии (8) — тоже (адрес хранилища ему не
нужен), но он стоит внутри отрезка: хрупок отрезок 5–9. Конструктор хранилища сверяет связность и при любом расхождении отказывает
`NotLinked(часть)`: у бухгалтерии нет кода или её владелец (`params().owner`) — не он сам; у ноги нет кода или её `vault()`
— не он сам; `legA == legB`.

**Кто кого знает.** Бухгалтерия — адреса реализаций (память, пишет только конструктор, сеттера нет) и владельца
(память, конструктор, сеттера нет); нога — хранилище (`immutable`); хранилище — бухгалтерию и обе ноги (`immutable`).
Реализации не знают никого: они исполняются на памяти бухгалтерии.

**Почему вычисленный адрес CREATE, а не CREATE2 и не одноразовый `setVault`.**
- Окна захвата нет: до шага 7 по адресу `V` нет ни кода, ни ключа (адрес CREATE не имеет приватного ключа), поэтому
  `onlyOwner` бухгалтерии и `onlyVault` ног вызвать некому. Код по адресу `V` может появиться только созданием от
  деплойера с nonce шага 7 — то есть ровно шагом 7.
- Одноразовый `setVault`/`setOwner` открывает окно между деплоем части и привязкой: кто первым позовёт, тот владелец; если
  ограничить его деплойером — это лишняя транзакция и временный владелец-ключ, а конструктор хранилища не мог бы проверить
  связность в момент создания (привязки ещё нет).
- CREATE2 по initcode замыкается в круг: initcode хранилища несёт адреса бухгалтерии и ног, а их initcode — адрес
  хранилища. Разомкнуть круг можно только привязкой ПОСЛЕ создания (тот же `setVault`) или фабрикой, несущей весь initcode,
  — это и есть то, от чего ушли. Зависимость от nonce CREATE2 снимает; это решение плана деплоя, если оно понадобится.
- Цена — хрупкость порядка: любая транзакция деплойера между шагами 4 и 7 сдвигает nonce, хранилище встаёт на другой
  адрес, его конструктор отказывает (`NotLinked(ledger)`), и части 4–6 остаются бесхозными — денег в них ещё нет,
  они деплоятся заново (реализации 1–3 переиспользуются). Стенды: `test_constructor_refuses_unlinked_parts` (nonce потрачен — отказ), сверка C16.

**Манифест и проверка после деплоя** (`diff/pool_ledger_diff.pytxt`: `deploy_pool`, `postdeploy_check`; схема манифеста
`pool_deploy_manifest_v1` — адреса, codehash каждой части, деплойер, nonce хранилища, параметры, роли). Проверка судит:
1. `codehash` каждой части на цепи = манифесту (неизменяемый адрес не защищает от вредного кода, поставленного при деплое);
2. код каждой части = коду сборки байт в байт; у частей с `immutable` (хранилище, ноги, модуль аварии) — с обнулёнными
   `immutable`, а сами `immutable` = адресам бухгалтерии, ног, модуля аварии и сроку `DELAY` (у ног — адресу хранилища, у
   модуля — четырём срокам манифеста `roles.terms`);
3. владелец бухгалтерии (её слот памяти по раскладке) и `vault()` обеих ног = хранилищу манифеста; `ledger()`, `legA()`,
   `legB()`, `emergency()`, `admin()`, `keeper()`, `guardian()`, `tvlCap()`, `legShareBps()` хранилища = манифесту;
4. адреса реализаций в памяти бухгалтерии = манифесту;
5. раскладка памяти всех реализаций бухгалтерии одна (`forge inspect … storageLayout`, без поля `contract`) — иначе
   реализация писала бы делегированным вызовом в чужие слоты; этот же гейт стоит в `selftest` (C9/C10).

Репетиция на своей цепи (сети не касается): `python contracts/diff/pool_ledger_diff.pytxt rehearse-deploy --out m.json` —
печатает размеры, деплоит в этом порядке, пишет манифест и прогоняет проверку. ⚠ Проверку против настоящей цепи этот
модуль не делает (его клиент знает только локальный anvil); перенос её в скрипт деплоя — шаг плана деплоя.

После деплоя и до первого депозита: активировать на Core хранилище и обе ноги (выплата и раздача на неактивированный адрес
отклоняются `NotActivated`), `initPartner` начальных партнёров (бухгалтерия принимает их только до первой операции).

## Изменения хранилища 17.10 (пакет безопасности, часть без решений оператора)

- **Заявки при открытом расчёте.** `processWithdrawals` пока открыт недельный расчёт пачками (`mondayBegin` …
  `mondayEnd`, флаг `status()[11]` бухгалтерии) отклоняется ЦЕЛИКОМ — `MondayOpen()`. Раньше бухгалтерия отвергала
  каждую заявку (`monday in progress`), хранилище ловило это как `WithdrawRejected` и сдвигало `nextIntent`: заявки
  пропадали. Теперь очередь не трогается и исполняется после `mondayEnd`. Прочие отказы бухгалтерии (сумма больше
  доступного, не инвестор) по-прежнему событие, а не остановка очереди.
- **Самореферал.** `register(referrer, payout)` с `referrer == msg.sender` отклоняется (`SelfReferrer()`). Бухгалтерия
  отвергает такой первый депозит (`deposit: self referrer`), а повторить `register` нельзя — адрес был бы навсегда закрыт
  для депозитов. Отказ регистрацию не расходует.
- **Смена admin в два шага.** `proposeAdmin(a)` (admin) ставит `pendingAdmin = a`, `pendingAdminEta = now + DELAY`;
  `acceptAdmin()` зовёт САМ предложенный адрес (может быть контрактом, например Safe) не раньше `eta`; `cancelAdmin()`
  (admin) снимает предложение. Повторное предложение (в том числе того же адреса) заменяет прежнее и отсчитывает `DELAY`
  заново — подменить безобидное предложение злым за секунду до срока нельзя. Одношаговый `setAdmin` удалён. `DELAY` —
  immutable, последний аргумент конструктора, умолчания нет: значение (таймлок) — решение оператора; `0` допустим и
  означает «принять можно в том же блоке» (сохраняется защита от опечатки адреса). ⚠ 18.10: механизм переписан в общий
  таймлок (`proposals[kind]`, `cancel(kind)`), `pendingAdmin`/`cancelAdmin` сняты; `setKeeper` и `legAddApiWallet`
  тоже ушли под него — раздел «Роли и доверие».
- **Пауза депозитов.** `pauseDeposits()` / `unpauseDeposits()` (admin; с 18.10 ставит и guardian). Под паузой
  отклоняется ТОЛЬКО `creditDeposit` (`Paused()`); `requestWithdraw`, `processWithdrawals`, `claim`, `claimFor`,
  `payQueue`, `treasuryPayout`, `coverShortfall`, `refundDeposit`, расчёт (атомарный и пачками) и торговля работают. Права
  на постановку паузы проверяет одна точка — модификатор `onlyPauser`; роль сторожа (guardian) добавляется туда одним
  условием. Снимает паузу только admin. `Send`, пришедший во время паузы, keeper возвращает отправителю `refundDeposit`
  (раздел «Возврат Send»).

Мутанты хранилища — один раннер: `python contracts/diff/pool_ledger_diff.pytxt mutants --vault --all` (словарь
`VAULT_MUTANTS` и `VAULT_EM_MUTANTS`, судья — `forge test --match-contract "PoolVault(Emergency)?Test"`; образец обязан
встречаться ровно один раз — судит и `selftest` C7/C7c; исходник восстанавливается и сверяется по sha). Новые мутанты
хранилища — в эти словари. ⚠ Части `--range A:B` гонять ТОЛЬКО в разных ворктри: раннер пишет мутант прямо в исходник
своего дерева и собирает его `out/`, и два процесса в одном дереве подменяют друг другу исходник (раздел «Слияние»).

## Возврат Send (`refundDeposit`, П3 / V3 пакета безопасности)

`refundDeposit(to, amountWei, ledgerRef, reason)` (keeper): `Send` USDC на Core хранилища, который бухгалтерия НЕ зачла
(ниже минимума, предел адресов, долг пула, treasury, пауза), возвращается **отправителю** — решение оператора 18.10:
«выводить туда, откуда пришло». Порядок: окно перевода ноги открыто — отказ `LegBusy` (неподтверждённый приход с ноги
выглядит излишком, как у притоков); адресат — не ноль, не хранилище и не его ноги (`BadRecipient`), Core-пользователь
(`NotActivated`: отправитель активирован по определению, и комиссия активации на хранилище не ляжет); сумма > 0;
`ledger.refundRef(ref)` — ref сгорает в общем пространстве депозитов и `coverShortfall` (повтор, возврат зачтённого,
зачисление возвращённого — `ledger_ref used`; при открытом расчёте — `monday in progress`); `spotSend` ровно `amountWei`
(wei Core, 8 знаков — с хвостом мельче микро); `_out(amountWei)`; событие `DepositRefunded(to, token, amountWei, ledgerRef,
reason)` (`token` = 0, USDC; с 20.10 — сигнатура сторожа). Деньги возврата — только излишек кассы: замок G1 после вызова судит `core − outPending − held >= 0`, а
`outPending` несёт этот возврат и ВСЕ исходящие блока (фантом после `claim`/`sweep` возвратом не взять — Н5 плана). Пауза
возврат не трогает. ⚠ Контракт не видит, кто прислал `Send` (граница (1) шапки `PoolVault`): адресата называет keeper по
записи леджера, сторож сверяет. Возврат не-USDC (A11) не реализован — решение оператора открыто.

Стенды `PoolVaultTest`: `test_refund_below_min_send_to_sender_and_burn_ref` (минимум 10 USDC, хвост мельче микро, повтор и
зачисление тем же ref, зачтённый ref), `test_refund_only_surplus_counts_outgoing_of_block` (денег нет; два возврата сверх
излишка в одном блоке и в следующем; фантом после выплаты в том же блоке), `test_refund_refused_while_leg_window_open`,
`test_refund_recipient_checks_pause_and_monday`. Мутанты хранилища (+8): без сжигания ref, без `outPending`, при открытом
окне ноги, на хранилище или ногу, неактивированному, нулевой суммы, без прав keeper'а, пауза отклоняет возврат.

**Почему замена guardian под таймлоком, а не сразу.** Guardian отменяет предложения admin'а — это единственная защита
таймлока от захваченного admin'а, кроме выхода инвесторов за `DELAY` (а выход за 48 ч не гарантирован: позиции,
возврат с ног, FIFO руками keeper'а). Мгновенная замена дала бы захваченному admin'у сначала поставить своего guardian,
потом провести любое предложение за `DELAY` без отмены. Цена: заменить скомпрометированный guardian можно только за
`DELAY`; всё это время он умеет только отнимать (паузу и отзывы admin снимает сразу), а свою замену отменить не может —
иначе удерживал бы роль вечно.

**Чего guardian НЕ даёт (названо, ревью 18.10).** (1) Вето обходится: захваченный admin сначала меняет guardian (её
guardian не отменяет), потом проводит предложение — окно выхода инвесторов `2·DELAY`, а не `DELAY`; сторож обязан
тревожить на `Proposed(2, …)`. (2) `revokeAgent` — вред не только живости: пока ключ отозван, позиции ноги никто не
закрывает, и цена может быть денежной (ликвидация); захваченный guardian может повторять отзыв, пока его не заменят,
а `cancelLegOrders` — снимать защитные стопы ноги (та же денежная цена).
(3) `restoreKeeper`/`restoreAgent` мгновенны — захваченный admin снимает отзыв guardian'а в том же блоке (новой силы
это не даёт: адрес уже прошёл таймлок). (4) Посторонний `Send`, не зачислимый (пауза, окно, лимит TVL), лежит излишком до
возврата V3; донат сверх лимита TVL закрывает приём до `setTvlCap` — лимит не ставить впритык к ожидаемому TVL.

**Таймлок — один механизм.** `proposals[kind] = {hash, eta}`, `hash = keccak256(abi.encode(аргументы))`. Перезапись того же вида (в том числе тем же действием)
сдвигает `eta` на `now + DELAY` — подмена безобидного предложения злым за секунду до срока не проходит. Исполнение
сверяет хеш и срок и снимает предложение; `cancel(kind)` — admin любое, guardian любое, кроме своей замены; созревшее
объявление аварии (вид 7 после `eta`) не снимает и не перезаписывает никто (ревью 20.10, R5). `DELAY` —
immutable конструктора (на бете 48 ч, значение в параметрах деплоя). Аварийный выход взял этот же механизм (вид 7); роль
`auditor` (план доверия) обязана взять его же новым видом, а не заводить свой.

## Agent-ключи ноги: отзыв, отмена заявок, проверка назначения

Факты testnet (прогон `run_20261017T165433Z`, T1(б) и T1k, отчёт

**Отзыв** — `revokeAgent(leg, name, salt)`, guardian или admin, сразу. Отзывается только ключ, применённый через
`applyAgent` (хранилище помнит его по `(leg, name)`); `restoreAgent` (admin) ставит ровно его. Замена — СВЕЖИЙ адрес
`address(uint160(uint256(keccak256(abi.encode(vault, leg, name, ++revokeNonce, salt, block.prevrandao, block.number)))))`;
событие `AgentRevoked(leg, agent, name, replacement)`.

- **Почему не константа.** Любой адрес, известный заранее, кто угодно делает Core-пользователем переводом 1 USDC — и
  отзыв перестаёт работать молча.
- **Почему соль вызывающего, а не `prevrandao`.** Документация HyperEVM о `prevrandao` молчит: страница
  [HyperEVM](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/hyperevm) говорит только «Cancun hardfork
  without blobs», [Interacting with HyperCore](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/hyperevm/interacting-with-hypercore)
  и [Raw HyperEVM block data](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/hyperevm/raw-hyperevm-block-data)
  о нём не пишут ничего, а у HyperBFT нет маяка RANDAO. Отсюда (**Inferred**, не замерено — замер требует сети):
  значение постоянно или известно до блока, и за непредсказуемое оно не принимается. `block.number`, `timestamp`,
  `blockhash(n−1)` известны до включения транзакции. Единственный вход, неизвестный третьему лицу ДО вызова, — `salt`:
  32 байта из CSPRNG на КАЖДЫЙ отзыв, никогда не переиспользовать; ноль отклоняется (`ZeroSalt`). `prevrandao` оставлен
  в хеше: если он окажется случайным, он только добавляет. Счётчик `revokeNonce` гарантирует разные адреса у двух
  отзывов даже в одном блоке с одной солью.
- **Замена, уже ставшая пользователем в начале блока** (соль утекла или переиспользована), — `AgentIsUser(replacement)`,
  повторить с новой солью. Тот же отказ у `applyAgent` и `restoreAgent`: Core-пользователя Core отверг бы молча.
- **Повтор разрешён.** Отзыв уже отозванного имени проходит (новый свежий адрес), чтобы guardian мог повторить молча
  отказавший отзыв без admin'а.
- ⚠ **Остаток.** После отправки транзакции соль видна в мемпуле HyperEVM: владелец украденного ключа может попытаться
  сделать адрес замены пользователем раньше, чем Core исполнит действие CoreWriter того же блока. Порядок L1-`Send`
  против действий CoreWriter одного блока не измерен. Закрывает это только проверка исхода (ниже) и повторный отзыв.

**Отмена висящих заявок** — `cancelLegOrders(leg, assets, oids)`, guardian или admin, сразу: нога шлёт CoreWriter-действие
10 «Cancel order by oid» `(uint32 asset, uint64 oid)` на каждую пару (`hyper-evm-lib` `CoreWriterLib.cancelOrderByOrderId`;
действие 11 — по cloid — не подключено). oid'ы даёт вызывающий: info `frontendOpenOrders` по ноге и ПО КАЖДОМУ дексу (без
`dex` builder-заявки не видны). Событие `LegOrdersCancelled(leg, oids)`. ⚠ Документация HyperCore пишет, что
«order actions … sent from CoreWriter are delayed onchain for a few seconds» — отмена через контракт исполнится с этой
задержкой. ⚠ Что отмена контракта снимает заявки, поставленные agent'ом от имени ноги (и триггерные), — **Inferred**
(заявки agent'а — заявки счёта ноги), на testnet НЕ проверено. Запасной путь, проверенный testnet (T1(б)): новый
agent ноги (через `proposeAgent`/`applyAgent`, то есть за `DELAY`) снимает висящие заявки отозванных ключей.

**Требование к keeper'у и сторожу (контракт этого не видит: прекомпайла ролей нет).**

1. После каждого `AgentSet(leg, agent, name)` и `AgentRestored`: info `{"type": "userRole", "user": agent}` обязан отдать
   `role == "agent"` и `data.user == адрес ноги`. Иначе — ТРЕВОГА, ключ не использовать (его заявки ушли бы в книгу
   чужого счёта, T1k): отозвать `revokeAgent` и назначить другой адрес. Ключ генерировать свежим и нигде больше не
   регистрировать.
2. После каждого `AgentRevoked(leg, agent, name, replacement)`, начиная со следующего блока: `userRole(agent)` обязан
   отдать `missing`, а `userRole(replacement)` — agent'а ноги. Пока не так — ТРЕВОГА и повторный `revokeAgent` новой
   солью.
3. Сразу после отзыва — снять висящие заявки ноги: `cancelLegOrders` по `frontendOpenOrders` (каждый декс), со
   следующего блока перечитать и повторять, пока книга ноги не пуста. Не снимаются — запасной путь новым agent'ом.
   Порядок: сначала отзыв (старый ключ больше не ставит), потом отмена — иначе ключ доставит новые заявки.
4. Срок `validUntil` agent'а (около 180 суток) — тревога за `DELAY` + запас до истечения: продление идёт через таймлок.

**После заморозки** (ред. 9.4) отзыв и отмена работают так же, и с ревью-3 (R3-A) admin так же возвращает ровно
отозванный ключ (`restoreAgent`) и ставит новый таймлоком — закрыть позиции ног после заморозки может только agent.

**Аварийный путь (guardian, ключ человека).** `revokeAgent` -> проверка п. 2 -> `cancelLegOrders` до пустой книги ->
при неудаче отмены — `proposeAgent`/`applyAgent` нового ключа admin'ом (за `DELAY`) и снятие заявок им. Позиции ноги
отмена НЕ закрывает: без ключа их никто не ведёт (вред живости и, при движении цены, — деньгам), а `cancelLegOrders`
снимает и защитные стопы.

## Замки кассы и ликвидности (G1, G2), депозит на perp, лимит TVL

- **G1** (`_slack`, заменяет `_assertBacked`): `core − outPending − 100·(spot + evm + max(0, legFlow + venueCash)) >= 0`,
  иначе `VaultSlack(slackWei)`. `outPending` — `spotSend` хранилища ТЕКУЩЕГО блока (`claim`, `claimFor`, раздача): их
  прекомпайл ещё видит, без вычета их съел бы приток того же блока (Н5). `legFlow + venueCash` — деньги, ПОДТВЕРЖДЁННО
  пришедшие с ног и ещё не разнесённые бухгалтерией (`venueCash` растёт только раздачей, падает только в
  `_fundClaimable` — проверено по коду `PoolLedger`). `max(0, …)`: разнесено больше, чем пришло, — прежний замок
  `core >= held`. Выплата G1 не меняет (`held` падает ровно на то, на что растёт `outPending`), поэтому он судится после
  неё. Витрина `vaultSlack()` — для сторожа. `vaultSlackSigned()` (пакет A, F2) — тот же излишек БЕЗ обрезки не
  разнесённого снизу: только для фиксации U_s при заморозке (отрицательное `u` — деньги, которые бухгалтерия уже провела с ног,
  а они ещё на ноге; G1 их не засчитывает — сторона отказа, — а U_s обязан: иначе чужой незачтённый `Send` на ту же сумму
  ушёл бы держателям).
- **Окна ног** (форма валидации В1/В2 со сдвигом к «считать только подтверждённое»). `legSendToVault` и `sweepToLegs`
  открывают окно ноги: блок, сумма, касса ноги в начале блока. Отправка текущего блока в G1 не считается (В1); пришедшая,
  но не подтверждённая — излишек, а не обязательство, поэтому пока открыто любое окно, притоки (`creditDeposit`,
  `coverShortfall`, будущий возврат V3) отклоняются `LegBusy`. `confirmLegSend(leg)` / `confirmSweep()` — любой
  вызывающий, блоком позже: отправка с ноги пришла, если касса ноги уменьшилась; раздача пришла, если касса выросла не
  меньше чем на сумму. Отказ раздачи проводится как пришедшее с ног, не разнесённое (эталон не меняется). Молчаливый отказ
  отправки с ноги не создаёт долга в G1 — `claim` не запирается ни до, ни после подтверждения (В2; в форме плана замок
  стоял бы до подтверждения). Окно одно на ногу; пока открыто — вторая отправка, `legToPerp`/`legToSpot` этой ноги и
  раздача отклоняются; перевод perp ↔ spot ноги закрывает её отправку и раздачу в том же блоке (касса начала блока была
  бы не кассой до перевода). Чужой `Send` на ногу в окне искажает вывод только платой не меньше суммы окна.
  ⚠ Видимость действия в b+1 — по докам interaction-timings; проба T1(а) обязана это подтвердить, иначе подтверждению
  нужен интервал из замера. ⚠ Касса ноги в окне движется только действиями хранилища, ПОКА agent-ключ ноги не торгует
  спот: спотовая сделка двигает spot USDC ноги и искажает вывод подтверждения (худшее — agent вместе с keeper'ом выдают
  отказавшую раздачу за пришедшую и зачисляют её сумму). Правило бота «ноги пула спот не торгуют» — условие замка;
  стандартный режим аккаунта (A3) в этом срезе не включается. ⚠ Вердикт подтверждения необратим: если Core исполнит
  перевод позже b+1, а подтверждение придёт раньше, раздача будет проведена как отказавшая (`legFlow` +сумма, затем
  деньги уйдут — `slack < 0`, лечится только внешним `Send` на хранилище: деньги с ног в G1 — обязательство, а не
  покрытие), отправка с ноги — как отказавшая (её деньги станут зачислимым излишком). Отсюда жёсткость требования T1(а).
- **Получатель обязан быть на Core** (`NotActivated`): выплата (`claim`, `claimFor`) и раздача на ноги отклоняются, если
  адрес не активирован (`coreUserExists`). Иначе Core списал бы с хранилища комиссию активации (1 USDC) мимо
  бухгалтерии, и G1 со следующего блока закрылся бы у всех. Держатель активирован своим депозитом (решение 18.10);
  реферал, ни разу не присылавший денег, копит награду до активации; ноги активирует деплой до первой раздачи.
- **G2** (`setWithdrawable`): `amount <= Σ_ног [withdrawable(нога) + spot(нога) − hold] + max(0, legFlow + venueCash)`,
  иначе `WithdrawableAbovePhysical(amount, physical)`. Неподтверждённые переводы не считаются (сторона отказа). Только
  декс 0 (ноги пула — только декс 0 и кросс-монеты, решение 18.10). Бухгалтерское `withdrawable` дальше только ужимается
  марками, поэтому судится точка записи; занятие маржи ботом после записи keeper обязан отражать новой записью вниз.
  Тот же G2 судит `withdrawable` бухгалтерии на `mondayBegin`: выплаты очереди в `mondayEnd` берут эту ликвидность, и
  откат `mondayEnd` по G1 при открытом расчёте оставил бы бухгалтерию запертой (`setWithdrawable` при `mondayOpen`
  отклоняется; выход — прислать деньги с ног). Остаток: рынок, сдвинувшийся между `mondayBegin` и `mondayEnd`.
- **Депозит на perp хранилища** (`usdSend`): `vaultToSpot(usd)` (keeper) — `usdClassTransfer` хранилища perp → spot, не
  больше выводимого perp хранилища (иначе Core отказал бы молча); затем `creditDeposit` как обычно. Отказ — возвратом V3
  отправителю (возврата в этом срезе нет).
- **Лимит TVL** (`tvlCap` конструктора, `setTvlCap` — admin, сразу; значение — оператор, умолчания нет): с 20.10 мера —
  капитал под управлением + депозит (`totalStake + amount <= tvlCap`, решение A10), раздел «Хранилище для беты».
  Прежняя мера «физические деньги хранилища и ног» снята: она закрывала приём от одной прибыли пула и зависела от порядка
  прихода двух `Send` (В11 пакета).

## Хранилище для беты (20.10): доля ног, заявки, лимит TVL, предел адресов, события

Решения оператора 18.10 (план `2026-10-17-pool-operator-decisions`, разделы «Решения 18.10*»): бета идёт на ОДНОЙ ноге
(C7), одна открытая заявка на адрес и «вывести всё» полем (A6), предел адресов пожизненный и поднимается под таймлоком
(A9), мера лимита TVL — «капитал + депозит» (A10). Правила бухгалтерии (эталон `runtime/vault_accounting.pytxt`) этим
шагом не менялись; в `PoolLedger` добавлены только сеттер параметра `raiseMaxInvestors` и витрина `totalStake`.

### Раздача ногам с долей (C7)

`sweepToLegs()` отдаёт ноге A `move · legShareBps / 10000` (округление вниз), ноге B — остаток; сумма ровно `move`.
`legShareBps` — ХРАНИМЫЙ параметр: задаётся конструктором (`VaultInit.legShareBps`, умолчания нет, > 10000 —
`BadAmount`) и меняется только общим таймлоком: `proposeLegShare(bpsA)` / `applyLegShare(bpsA)` (admin, вид 5,
`DELAY`, guardian может снять `cancel(5)`), событие `LegShareSet(bpsA)`.

Почему не аргумент `sweepToLegs(bpsA)`: доля решает, на каком счёте лежат деньги пула и какой бот ими торгует, — это
топология (какая нога живая, на каком IP), а не решение одной раздачи. С аргументом её выбирал бы keeper в каждом вызове:
ошибка или кража ключа keeper'а молча уводила бы деньги на ногу без бота. Цена хранимого параметра — смена топологии
(включение второй ноги) ждёт `DELAY`, и это приемлемо: вторая нога появляется «когда освободится место», а не в аварии.

Нога с нулевой долей не получает ничего: `_sendToLeg(leg, 0)` возвращается ДО проверки активации и окна, поэтому при
10000/0 нога B не обязана быть ни активирована, ни торгующей (стенд `test_sweep_share_all_to_leg_a_second_leg_untouched`
её не активирует). Замок G1 и `outPending` не тронуты: `legFlow −= move`, `_out(move · 100)` — как прежде, окно
открывается у каждой ноги, получившей деньги. `_legFree` обеих ног проверяется по-прежнему: перевод perp ↔ spot ноги B в
блоке раздачи её закрывает (бета этого не делает). На бете (`rehearse-deploy`, `deploy/params.beta.json`) — `leg_share_bps = 5000`:
две ноги по половине раздачи (решение оператора 21.10; до него — 10000, одна нога), обе ноги активируются на Core до
первой раздачи.

Стенды: `test_sweep_share_all_to_leg_a_second_leg_untouched` (10000/0), `test_sweep_share_half_and_all_to_leg_b`
(5000/5000 и 0/10000), `test_sweep_share_rounding_remainder_to_leg_b` (3333 bps на 900 000 007 микро: A 299 970 002,
остаток B), `test_leg_share_through_timelock`. Мутанты: доля игнорируется (50/50), остаток округления теряется, нога с
нулевой долей получает окно и проверку активации, без таймлока, выше 100 % при предложении и в конструкторе, без прав
admin, доля не записывается.

### Заявки на вывод: одна открытая, «вывести всё», проверка при подаче (A6, П5)

- `requestWithdraw(amount, reward, withdrawAll)`. **Одна открытая заявка на адрес** — `openIntent[a]`: ставится подачей,
  снимается в `processWithdrawals` в обоих исходах — исполнение (`WithdrawProcessed`) и отказ бухгалтерии
  (`WithdrawRejected`). Вторая при открытой — `IntentOpen()`. Счётчик один (флаг): второго K нет, рассинхрона двух
  счётчиков быть не может.
- **«Вывести всё»** — полем `withdrawAll` (план намерений D12): сумма обязана быть 0 (`BadAmount`), контракт пишет в
  очередь служебное `ALL = 2^256 − 1` (событие `WithdrawRequested` несёт его же), а при обработке спрашивает свободную
  долю НА ЭТОТ МОМЕНТ (`freeStake(a, reward)`) и выводит её. Свободная доля 0 к обработке — отказ бухгалтерии
  `withdraw: amount` событием. Точная сумма — `withdrawAll = false`, сумма > 0.
- **Проверка при подаче** (рекомендация A6, находка В4 пакета): `freeStake(msg.sender, reward)` обязан быть > 0 и не
  меньше суммы, иначе `AboveFree(amount, free)` — заявки не-держателей и сверх свободного не встают в очередь перед
  честными, и дорогой обход проекции платит заявитель, а не keeper. К обработке доля может упасть (убыток недели) — тогда
  отказ событием, как прежде.
- **Не сделано: минимум суммы заявки 10 USDC** (П5 «сумма ≥ минимума выплаты или всё»). Минимума выплаты в бухгалтерии
  нет (A5 решено вариантом (б) — правило бота), своего числа хранилище не заводит. Решение оператора: константа
  хранилища, параметр деплоя или правило ретранслятора.
- ⚠ Цена проверки при подаче — газ `freeStake` заявителя: проекция фазы 2 ред. 9.2.1. На простом пуле 0.13–0.16 млн
  (замер ниже), в худшем замеренном состоянии при n = 50 — до ~18.7 млн (раздел «Газ заявок»): такой вызов не помещается в
  малый блок HyperEVM (3 млн) и требует больших блоков. На бете (N ≈ 10, решение B10 (а): кошельки оператора) —
  **Inferred** приемлемо; для публичного запуска — пачечная проекция (ниже) или проверка ретранслятором.

Стенды: `test_one_open_intent_per_address`, `test_request_checks_free_stake_at_submission`,
`test_withdraw_all_takes_free_stake_at_processing` (доля выросла после подачи — выводится 1 500, а не 1 000),
`test_withdraw_rejection_outside_monday_is_still_an_event` (отказ снимает `openIntent`, очередь идёт дальше),
`test_intent_sequences_never_make_processing_revert` (160 случайных шагов подач — точных, «всё», лишних — обработок

### Газ заявок: keeper не «съедает» заявку нехваткой газа (§4.2 намерений; бухгалтерия без `try`, отказ — кодом)

**Правило (пакет A ревью, 20.10).** Бизнес-отказ вывода бухгалтерия возвращает КОДОМ, а не отказом транзакции:
`PoolLedger.withdraw(a, amount, reward) -> (status, paid, queued)`, `status` — `W_OK` (0), `W_AMOUNT` (1: сумма 0 или больше
свободной доли — эталон `withdraw: … при доступных …`), `W_RANGE` (2: сумма вне uint128 — эталон `_amount`). Это ВСЕ
бизнес-отказы эталона `withdraw`; `free_stake` отказов не имеет (витрина). Отказ кодом проверяется до первой записи —
состояние не тронуто, `paid = queued = 0`. Прочие отказы эталона (нулевой адрес, заморозка, открытый расчёт), инварианты и
газ — отказ транзакции, как прежде. Хранилище зовёт `freeStake` (у «всё») и `withdraw` БЕЗ `try`: любой их отказ — в том
числе нехватка газа на ЛЮБОЙ глубине — откатывает ВСЮ транзакцию: `nextIntent` и `openIntent` на месте, часы `T_serve`
не сброшены. Отказ кодом уходит событием `WithdrawRejected(id, Revert(string))` с прежней причиной (`withdraw: amount`,
`uint128`) — сторож и журнал читают его как раньше; код вне известных — отказ транзакции (`BadAmount`).

**Почему не эвристика по газу (находка ревью R2/R2b/R2c, HIGH).** Прежнее правило `_assertNotStarved` (`gasleft() < g/63`
после отказа = нехватка газа) судило порог EIP-150 ОДНОГО фрейма, а `withdraw`/`freeStake` уходят в проекцию через
статический вызов бухгалтерии самой себя (`_projCall`, PoolLedger.sol): при нехватке газа ВНУТРИ неё вызов отказывает
пустым ответом, когда у хранилища остаётся больше `g/63`. Ревью (`ReviewEmergency` R2c, книга 30 держателей × 5 поколений
с бумажным убытком) находило полосу газа, где заявка СЪЕДАЛАСЬ (событие отказа, заявка снята, капитал не тронут), и R2b —
что так keeper бесконечно сбрасывает `T_serve`. Сейчас тот же скан: «OOG-revert» с 300 000, «EXECUTED» с 1 758 000, полосы
«EATEN» нет; R2 — съеденных 0 из 287 уровней (276 откатов, 11 исполнений), R2b — «съедающего газа нет»; `ReviewNestedOog`
(3 держателя, шаг 1 000) — съеденных 0 у точной и у «всё».

⚠ **Цена правила.** Заявка, на которой бухгалтерия откатывается ДЕТЕРМИНИРОВАННО (не газ: инвариант, сбой), останавливает
очередь до правки причины. Это сознательный выбор: остановка громкая (keeper видит отказ, сторож — стоящую очередь, авария —
`T_serve`), а съеденная заявка — потеря без следа. Законных бизнес-отказов, которые до 20.10 уходили событием, это не
касается: они приходят кодом.

### Лимит TVL: капитал под управлением + депозит (A10)

`creditDeposit` отклоняет `TvlCapExceeded(capital, cap)`, если `totalStake + amount > tvlCap`, где `totalStake` —
новая витрина бухгалтерии (`PoolLedgerViews.totalStake()`, одно чтение `stakeSum`, эталон `total_stake`). Ровно на
лимите — принят, +1 микро — отказ. Прежняя мера «физические деньги хранилища и ног» снята вместе с `_physical()`:
она закрывала приём от одной ПРИБЫЛИ пула (прибыль на ногах до расчёта недели — не капитал) и зависела от порядка прихода
(два `Send` при запасе под один — отвергнуты оба, оба уже на Core). Новая мера: прибыль становится капиталом только
расчётом недели (и тогда входит — это и есть «капитал под управлением»), вывод освобождает место сразу. ⚠ Мера
keeper-зависима так же, как всё остальное: лимит — граница кражи keeper'ом через зачисление, но не через
`closePosition` (Н7). `setTvlCap` — admin, сразу, как прежде. Стенды: `test_tvl_cap_is_capital_plus_deposit`,
`test_tvl_cap_profit_does_not_close_intake`, `test_tvl_cap_does_not_depend_on_arrival_order`. Мутанты: `<=` → `<`,
депозит не входит в меру, лимит не проверяется.

## Расчёт чаще недели (#1): что проверено

Keeper проводит расчёт раньше недели, когда газ шага приближается к лимиту большого блока. ⚠ **Ревью-3b:** календарный расчёт
теперь — не чаще одного за календарную неделю (`block.timestamp`, неделя от понедельника 00:00 UTC; раздел «Ревью-3b»), частый
расчёт — только внеочередной по праву; стенд ниже переписан так (расчёты 2 и 3 — внеочередные). Текст до конца абзаца — дерево
ревью-2. Бухгалтерия частого расчёта не
запрещает: часов у неё нет, `week` — СЧЁТЧИК РАСЧЁТОВ. Стенд `test_review2_three_settlements_in_one_week` (атомарный, пачками,
атомарный — в одну календарную неделю): каждый принят, `week` +1 на расчёт, `mondayEndAt` = время расчёта, триггеров нет,
`liveGenCount` уходит ровно с закрытием ордеров поколения; заявка в очереди бухгалтерии стареет от РОЖДЕНИЯ
(`T_QUEUE_MAX` расчёты не молодят — журнал `qStamps` датирует заявку операцией, в которой она родилась, и уже стоящую
заявку не перештамповывает), `T_NOMONDAY` — от последнего
расчёта, `T_STUCK` — от открытия пачками. Эти часы чинить не пришлось.

Названо, кодом не чинится (семантика, а не поломка инвариантов; починка — календарная неделя в эталоне и фикстурах,
отдельный проект). **Ред. 9.5 это закрыла:** внеочередной расчёт `monday(false)` неделю не сдвигает (срок партнёра — в
календарных неделях, фикстура 264); частый расчёт теперь — `monday(false)`, а `monday()` — ровно календарная неделя:
* **Партнёрский срок считается в расчётах.** `_refRate`: `week > max(firstWeek, sinceWeek) + partnerTermWeeks` — каждый
  внеплановый расчёт сокращает календарный срок партнёра. В бете партнёров нет (`partners: []`), число инертно. Если admin
  заведёт партнёра (`setPartner`), keeper обязан вести счёт внеплановых расчётов, а `partnerTermWeeks` — задаваться в
  расчётах.
* **Комиссия с максимума (HWM) фиксируется на каждом расчёте.** Дважды с одной прибыли она не берётся (максимум
  поднимается), но на пути «вверх — вниз» более частый расчёт видит больше вершин: комиссия >= недельной на том же пути.
  Это свойство частоты фиксации, решение — у оператора (частоту задаёт keeper по `liveGenCount`).
* Требование к keeper'у и сторожу (ветка `work/vault-keeper`, их код здесь не проверялся): событие `MondaySettled` и рост
  `status()[1]` — по расчёту, а не по календарной неделе; несколько за неделю — норма.

# Ред. 9.5 (21.10): амортизация поколений и внеочередной расчёт

Эталон — `work/vault-gen-bound` @`70eccba5` (влит `9e487690`): `GenLedger(max_gens)`, `monday(calendar)`, фикстуры 262–269,
спека 8.15. Решения оператора: амортизация правил НЕ меняет (дифференциал по всем прежним фикстурам бит в бит, плюс 262–269);
внеочередной расчёт неделю не сдвигает, право на него контракт судит сам; `maxGens` — жёсткий предел, параметр деплоя из
замера газа.

## Что в контракте

**Амортизация (правила раздела те же).** Всё, что расчёт делал обходом ВСЕХ поколений, ведётся там, где меняется R, марк или
состояние ордера:

| величина | что | пишет | заменяет обход |
|---|---|---|---|
| `shareSum[g]` | Σ_a доля(a, g, R_g) | `_aggR` (та же сумма разниц, что `aggPend`) | `colSum` строк расчёта |
| `growSum` | Σ_{g ∈ снимки} max(0, R_g) + genUpos_g | `_moveR`, `_setUpnl`; финализация снимает окончательные | `_stakeCeiling` (марк, закрытие, депозит) |
| `lossRN`, `lossOpenN` | поколений с R < rMon / с бумажным убытком | `_moveR` / `_setUpnl`; начало фазы 2 обнуляет `lossRN` | `_noProjectedLoss` |
| `snapTotalSum` | Σ весов снимков | `sizeOrder`; финализация снимает окончательные | P замороженного пула (`emergencyFreeze`) |
| `gensSince` | поколений с последнего расчёта (эталон `_gens_since`) | `sizeOrder` +1, расчёт — 0 | — (предел) |

* **Окончательное поколение** — не текущее и без живых ордеров: ордер встаёт только в текущее (эталон `size_order`), значит
  ни ордера, ни результата в него больше не придёт. Оно закрывается в момент, когда стало окончательным (`_genDead`: в
  `cancelOrder`, в закрытии `closePosition`, в `sizeOrder`, открывающем новое поколение, — прежнее текущее): проверка
  `shareSum <= R` («разнесено больше, чем заработано» эталона), пыль R − shareSum и R копятся (`dustPending`,
  `closedPending`), поколение уходит из списка живых. Снимок, R и rMon остаются до расчёта: их читают строка должника, раздел
  недостачи и выгрузка (эталон держит поколение в `snaps` до конца `monday`).
* **Снимки** (`snaps` эталона) — пережившие прошлый расчёт `surv[0..survN)` и все открытые после него (genBase, gen]: номера
  поколений идут подряд, расчёт их не открывает, поэтому список не хранится (`_genAt`, `_snapCount`, `_genIndex`). **Живые**
  (текущее и с живыми ордерами) — двусвязный список по возрастанию (`lvHead`/`lvNext`).
* **Строка не-должника** — O(1): результат недели = `aggPend` (ведётся `_aggR` на каждом изменении R). **Строка должника** —
  убыток по поколениям читается ПАЧКАМИ единиц строк (`_scanLoss`: единица — поколение снимков, сразу за строкой должника),
  в буфер идут только ненулевые пары (поколение, убыток) по возрастанию поколения (`monLossG/V`, `monDebtOff`) — тот же порядок
  кандидатов `_split`, что у прежних G слов с нулями. Исход от нарезки не зависит: строки не меняют R и rMon.
* **Финализация** — O(живых): пыль окончательных одной суммой в котёл (зачисление в котёл аддитивно, пыль >= 0 — сумма та же,
  ноль ровно когда нули все), R — в `closedR`; среди живых без ордеров бывает только ТЕКУЩЕЕ (иначе — отказ «dead generation
  left live»), оно закрывается тем же `_genDead`; пережившие становятся `surv`. Начало фазы 2 пишет `rMon := R` только живым;
  в фазе 2 `col` всех — доля R (`_colIsR`).
* **Проекция** `_holdAt`: `_worstOf` останавливается, как только сумма дошла до границы `_holdAt` (максимум по поколениям только
  растёт — ответ тот же). Без этого первый должник по маркам стоил n·G чтений веса (164 тыс. газа на поколение при n = 43).
* **Книга ордеров** (fill, cancel, mark, close, reduce) вынесена в `PoolLedgerBook` — шестую реализацию на памяти `PoolLedger`
  (`Init.bookImpl`): в `PoolLedgerMonday` (запас был 476 Б) с амортизацией она не помещалась. Проверки не урезаны.

**Внеочередной расчёт.** `monday(bool)`, `mondayBegin(bool)` (бухгалтерия и хранилище; `monday()`/`mondayBegin()` — прежние,
календарные): `false` — тот же расчёт, неделя не сдвигается (срок партнёра, `firstWeek`, возраст заявок, `sizedWeek` —
календарные), `gensSince := 0`. Метки буферов фазы 2 (`monDebtPos`, `monRepayPos`, `monGive`) — номер расчёта `monEpoch`, не
неделя: при двух расчётах одной недели метка недели сочла бы чужие записи своими. Неделя снимка аварии посреди внеочередного
расчёта — текущая (`monCal`).

**Право на внеочередной расчёт** (бухгалтерия, `_extraAllowed`; иначе `monday: extra settle not allowed`, состояние не
тронуто): открыто поколений с последнего расчёта `gensSince >= ⌊maxGens/2⌋` ИЛИ в этом блоке есть должник по маркам
(`projectedShortfall() > shortfall` — та же величина, что у гейта депозита, O(адресов), без раздела). «Открыто поколений» —
счёт с расчёта (`gensSince`, его и режет предел), а не число снимков `liveGenCount()`: долгоживущие поколения расчётом не
закрываются, и по ним клапан открывался бы без конца. `maxGens = 0` — «правила нет» эталона: условие пусто (так у фикстур
эталона, где внеочередной расчёт — политика keeper'а); хранилище с такой бухгалтерией не связывается (`NotLinked`), проверка
после деплоя тоже отказывает.

**Предел.** `sizeOrder`, которому нужно НОВОЕ поколение при `gensSince >= maxGens`, — отказ `size_order: max_gens`; ордер при
тех же весах встаёт в текущее и пределом не режется. Витрина `genLimits()` = (`maxGens`, `gensSince`, живых); `liveGenCount()`
— число снимков (`len(snaps)`).

**Изменения ABI.** `PoolLedger.Init` + `bookImpl`, `maxGens` (в конце); `monday(bool)`, `mondayBegin(bool)` у `PoolLedger` и
`PoolVault`; витрина `genLimits()`; деплой — 10 частей, хранилище — nonce 9 у свежего деплойера. Единица пачки этапа строк —
строка адреса ИЛИ поколение строки должника (`mondayProgress`: сделано = строк + поколений; стенд
`test_phase2_steps_block_everything_until_done` — `mondayStep(3)` вместо `(2)`).

## R3-A: agent-ключи ног после заморозки

`restoreAgent`, `proposeAgent`, `applyAgent` — модификатор `onlyAdminKeys` (только проверка admin, без замка `_live`); все
прочие admin-действия — по-прежнему `onlyAdmin` -> `_adminLive` (`_live` + та же проверка `_admin`). Права те же, что до
заморозки: `restoreAgent` ставит РОВНО отозванный ключ и сразу (он уже прошёл таймлок); новый ключ — только таймлоком
`DELAY`, и `cancel` guardian'а замка не имеет — вето на месте и после заморозки. Предложение ключа, созревшее до заморозки,
исполняется и после неё (оно прошло тот же таймлок). Отзыв ключа и отмена заявок — как были (`onlyPauser`, без замка).

**Денежных путей возврат ключа не открывает.** Agent-ключ ставит и снимает заявки счёта ноги, денег хранилища он не двигает;
после заморозки по-прежнему `Frozen` у каждой операции keeper'а (депозит, раздача, переводы ног, заявки, возврат `Send`), у
`register`/`requestWithdraw`, у прочих admin-действий (роли, доля, лимит, TVL, партнёры, объявление). Деньги ног в
хранилище сводит `emergencyCollect` (кто угодно), раздаёт `emergencyClaim` — как в ред. 9.4.

⚠ Цена (принята решением): захваченный admin после заморозки может мгновенно снять отзыв guardian'а (`restoreAgent`) —
ровно та же сила, что до заморозки (раздел «Роли и доверие», (3)); новый ключ — только через `DELAY` под вето guardian'а.

Стенды (`PoolVaultEmergencyTest`): `test_review3_frozen_agent_revoke_is_reversible` (guardian отзывает после заморозки,
guardian и посторонний вернуть не могут — `NotAdmin`, admin возвращает ровно отозванный; бухгалтерия бит в бит, деньги
хранилища и ноги на месте, keeper/инвестор/прочие admin-действия — `Frozen`, держатель забирает ровно своё),
`test_review3_revoked_before_freeze_restorable_after` (отзыв до заморозки, возврат после),
`test_review3_frozen_new_agent_only_through_timelock` (guardian и посторонний не предлагают и не применяют; до `eta` —
`TooEarly`; `cancel` guardian'а после заморозки снимает предложение; новое предложение через `DELAY` применяется; денежные
пути закрыты). Репро ревьюера `test_r3_frozen_agent_revoke_is_one_way` и `test_r3_revoked_before_freeze_never_restorable` на
этом дереве КРАСНЫЕ (`restoreAgent` больше не откатывает — восстановление возможно).

## R3-B: сверка keeper'а без ноги не на Core

`reconcile()` обходит обе ноги и ногу без Core-аккаунта пропускает, не читая её прекомпайлов — так же, как G2
(`_physWithdrawable`) и `emergencyCollect`. Стоимость ног — Σ `accountValue` + (Σ spot ног в wei) / 100: spot суммируется в
wei и делится на микро один раз, как прежде (сумма — в `uint256`, прежде — `uint64`). Стенды:
`test_review3_reconcile_skips_leg_not_on_core` (бета 10000/0, прекомпайлы ноги B откатывают — сверка считает perp + spot
ноги A = 900), `test_review3_reconcile_two_legs` (две ноги, perp обеих, по 50 wei остатка на каждой — +1 микро). Репро
`test_r3_reconcile_reads_unactivated_leg_b` на этом дереве КРАСНЫЙ (`reconcile()` не откатывает). Keeper (`work/vault-keeper`)
считает сверку сам при доле B = 0 — после выкатки этого дерева он может перейти на витрину.

## R3-I: регистрация после первого депозита

`register` отвечает `AlreadyRegistered`, если адрес уже вносил деньги (`isInvestor` бухгалтерии) — тем же отказом, что и
повторная регистрация: режим выплат и реферала бухгалтерия принимает только первым депозитом. Режим выплат после первого
депозита меняет `setPayoutMode` (инвестор сам), реферала не меняет ничто. Предикат «первый депозит» один — `_old(a)`, его
зовут и `creditDeposit`, и `register`. Регистрация до первого депозита — как прежде. Стенд
`test_review3_register_after_first_deposit_refused`. `test_credit_deposit_first_by_is_investor` переписан: регистрация до
первого депозита, затем `setPayoutMode(false)` и пополнение — режим регистрации, переданный повторно, бухгалтерия отвергла бы
(`deposit: payout mode`). Без смены режима стенд мутанта «первый депозит — всегда» НЕ ловил (повтор того же реферала и режима
бухгалтерия принимает) — мутант выжил в первом прогоне и пойман после правки стенда.

## Принято остатком

* **R3-M.** Agent ноги может необратимо перевести счёт ноги в unified. Замер testnet 21.10 (`work/vault-keeper`, раздел
  R3-M справочника keeper'а): `agentSetAbstraction "u"` переводит счёт в `unifiedAccount`, обратный переход agent'ом —
  отказ «Abstraction transition not allowed». В контракте вернуть режим нечем: у `TradingLeg` нет входа на CoreWriter-действие
  16 (`setAbstraction`, в `hyper-evm-lib` оно есть), а пропустит ли венью `unified -> disabled` от самого счёта — НЕ проверено
  (**Unverified**), поэтому вход не добавлен: непроверенный путь возврата выглядел бы защитой. Режим меняет смысл прекомпайлов
  сверки и вывода (perp `accountValue` = 0, деньги в spot). Защита — снаружи: keeper каждый шаг читает `userAbstraction` ног

## MEDIUM: календарный расчёт — не чаще одного за календарную неделю

До правки `monday()`, `monday(true)`, `mondayBegin()`, `mondayBegin(true)` не ограничивал НИЧТО: право (спека 8.15) судило
только внеочередной расчёт, а календарный keeper проводил сколько угодно раз, в том числе в одном блоке. Цена: комиссия
фиксируется с пика (путь +200 / −200 внутри недели — 100 USDC комиссии с недели с нулевым итогом), а срок партнёра
(`partnerTermWeeks`, неделями `week`) сжигается за блок (52 расчёта подряд).

**Правило.** `_mondayBegin(calendar)` — ЕДИНСТВЕННЫЙ вход всех четырёх форм — принимает календарный расчёт, только если номер
календарной недели больше номера недели прошлого календарного расчёта; иначе `Revert("monday: calendar week already
settled")`. Номер недели — `_calWeek() = (block.timestamp + 3 days) / 7 days`: неделя — 7 суток от понедельника 00:00 UTC
(Unix-эпоха 1970-01-01 — четверг, ближайший понедельник не позже неё — 1969-12-29, на 3 суток раньше). Своих чисел нет —
только 7 суток и эпоха понедельника. Память — одно слово `calNext` (неделя, с которой календарный расчёт снова допустим;
0 — расчётов не было). Внеочередной расчёт (`calendar = false`) — по прежнему праву, календарь не трогает: календарный той
же недели после него проходит.

**Это свойство контракта, а не эталона.** Времени в эталоне нет, каждый его календарный расчёт — новая неделя; эталон не
тронут. Харнесс дифференциала перед КАЖДЫМ календарным расчётом (атомарным и пачками) сдвигает цепь на 7 суток
(`Ledger.next_week`, `evm_increaseTime`) — номер недели следующего блока растёт ровно на единицу; внеочередной время не
двигает. Стенды бухгалтерии, которым время безразлично, перед календарным расчётом переходят в начало следующей недели
(`test/CalendarWeek.sol`, `toNextCalendarWeek`).

**Keeper'у не мешает** (код `work/vault-keeper` читался, не менялся): расписание — `Mon *-*-* 04:00:00 UTC`
(`hl-followk-weekly.timer`, `monday_schedule`), расчёт один на ISO-неделю (`monday_st[iso]`), а ISO-неделя начинается в
понедельник 00:00 UTC — ровно граница `_calWeek`. Первый календарный расчёт каждой недели проходит; повтор после падения
keeper идемпотентно сверяет по `status()[1]` и второго вызова не шлёт. ⚠ Пропущенную неделю догнать вторым календарным
расчётом в следующей неделе теперь нельзя: `week` отстанет от календаря на единицу навсегда. Keeper на этот случай уже
останавливает деньги (`_monday_step`: `week` контракта не `e − 1` и не `e` — `halt_money`, решение оператора: сдвинуть
якорь `first_settle_iso_week`).

**LOW: причина отказа внеочередного.** `_extraAllowed()` зовёт `_start()` первым: на замороженном пуле — «frozen», в открытом
расчёте — «monday in progress», а не «monday: extra settle not allowed». Запись `initialized` откатывается вместе с отказом.

Стенды (`PoolLedgerGensTest`): `test_rv3b_second_calendar_in_a_week_refused` (внеочередной отклонён — календарный того же
блока принят ОДИН раз, все четыре формы второго — отказ, неделя +1, следующая неделя пачками проходит),
`test_rv3b_peak_fee_via_calendar_refused` (календарный на пике той же недели — отказ; комиссия на обоих путях 0),

## Принято остатком беты (доверие к keeper'у оператора)

* **Внеочередной расчёт тоже фиксирует комиссию с текущего максимума, а право на него keeper может набрать искусственно.**
  Поколение рождает вход после смены весов: марк якорной позиции + `sizeOrder` + `cancelOrder` — без единой сделки. Замер
  (репро `test_rv3b_right_manufactured_by_size_cancel`, n = 2): 500 таких поколений — 340 069 175 газа, **~0.68 млн газа на
  поколение**; при `maxGens` = 1000 право (⌊1000/2⌋ = 500 поколений) стоит ~340 млн газа — дорого, но в пределах одного
  keeper'а за несколько часов малых блоков. Класс — «keeper оператора», как H7 (результаты сделок keeper сообщает сам):
  контракт не отличает искусственное поколение от торгового. Защита — ключ keeper'а у оператора, сторож (рост
  `genLimits().gensSince` без исполненных ордеров, внеочередные `MondaySettled` подряд). Календарную частоту теперь держит
  контракт; внеочередную — только право.
* **`maxGens` = 1000 выведен для ОДНОГО должника по маркам** (раздел «Предел поколений»). При нескольких должниках
